# herdr-succession

コンテキスト逼迫で判断の質が落ちたセッションを、後任へ**渡し切る**までのスキル。文書を書くところで終わらせない。後任が起動し、状態を自分で把握し、次の一手を持った状態にするまでが 1 単位。

引き継ぎが壊れるのは決まって後半 (起動・投入・検証) で、しかも壊れ方が毎回同じなので、罠は各段の中に置いてある。読み飛ばすと同じところで止まる。

## 前提チェック (最初に必ず)

```sh
test "${HERDR_ENV:-}" = 1
```

`HERDR_ENV=1` でなければ herdr 管理下の pane に居ない。Step 3 以降 (タブ生成・起動・投入・検証) が成立しないので、「herdr の外なので後任を立てられない。引き継ぎ文書だけ書きますか?」と 1 問確認して、文書だけで止まる。

親自身の位置は `HERDR_WORKSPACE_ID` / `HERDR_TAB_ID` / `HERDR_PANE_ID` で分かる。

## モード判定

| モード | 引き金 | 引き継がれる側 |
|---|---|---|
| **self** | 「引き継ぎたい」「コンテキストが限界」「後任を立てて」 | このセッション自身 |
| **child** | 「ABC-123 の子が逼迫してる」「あの子を引き継がせて」 | 子セッション 1 本 |

判断がつかなければ 1 問で確認する。self を child と取り違えると、他人のタブに引き継ぎ指示を投げることになる。

## 2 モードの違い

差があるのは Step 1・2 と後始末だけ。Step 3〜7 は共通。

| | self | child |
|---|---|---|
| 文書を書くのは | 自分 | **子** (親は代筆しない) |
| 実測する対象 | 自分の cwd | 子の `checkout_path` |
| 後任の cwd | 自分と同じ | 子と同じ worktree |
| 旧セッション | 落とさない。検証まで見届ける | 検証後に親がタブを閉じる |
| Linear | 触らない | 触らない (同じ issue の作業が続く) |

child モードでも **worktree は作らない**。同じ作業の続きなので、後任は既存の worktree にそのまま入る。

## Step 1: 引き継ぎ文書を書く

保存先・命名・テンプレは `~/.dotfiles/claude/handoff-policy.md` が正典。**Read してから書く。** このスキルには写さない (二重管理になり、片方だけ古くなる)。

冒頭の「踏んだ罠」を落とさない。ここが引き継ぎの本体で、状態は文書とリポジトリから復元できるが、踏んだ罠は書かなければ失われる。

**self モード** — 自分で書く。

**child モード** — 子に書かせる。親は子の会話文脈を持っていないので、代筆すると罠が丸ごと落ちる。親が知っているのは子の外形 (branch・commit・blocked の有無) だけで、どこで判断を誤ったかは子の中にしかない。

指示はファイルに書いて投げる (理由は Step 5):

```sh
herdr agent prompt <child-agent> "$(cat "$instruction_file")"
```

指示本文に入れるもの:

```
コンテキストが逼迫してきたので、後任セッションへ引き継ぎます。

~/.dotfiles/claude/handoff-policy.md を読み、その規約どおりに引き継ぎ文書を
書いて保存してください。

- 冒頭の「踏んだ罠」を必ず埋める。このセッションで実際に起きた失敗を、
  型ごとに実例 1 行で書く。無い型は行ごと落とす
- 「いまの状態」は記憶で書かず、コマンドで実測した値を書く
- 書き終えたら、保存先の絶対パスだけを最後の行に出力してください
```

保存先は `herdr agent read` で受け取る:

```sh
herdr agent read <child-agent> --source recent-unwrapped --lines 40
```

子がパスを返さない・保存に失敗した場合はそこで止める。文書が無いまま後任を立てると、後任は前任の罠を一切知らない状態で同じ場所を踏む。

## Step 2: 状態を実測して書く

**記憶で書かない。** 記憶で書いた箇所は実際に誤る。「完了」と書いた節が未完了だった / 「数がずれている」と書いた箇所がずれていなかった、という取り違えが両方起きている。

self は cwd、child は子の `checkout_path` を `-C` に渡す:

```sh
dir=<self なら "$(git rev-parse --show-toplevel)" / child なら checkout_path>

git -C "$dir" status --short                          # 作業ツリーの clean 判定と変更ファイル
git -C "$dir" rev-list --left-right --count @{u}...HEAD  # behind<TAB>ahead
git -C "$dir" log --oneline @{u}..HEAD                # 未 push のコミット
```

upstream が未設定なら `@{u}` は失敗する。その場合は `origin/<default-branch>...HEAD` に替える。**失敗を握り潰して 0 と書かない** — 空振りしたコマンドの結果を実測値として扱うのが、そもそも罠の 1 つ。

成果物があるなら数える:

```sh
wc -l <生成したファイル群>
```

child モードでは、子が抱えている孫セッションも数える (`herdr agent list` を自リポの workspace に絞る)。self モードでは自分が抱えている子セッション全部。pane・タブ label・`agent_status` を書く。

**取った値は Step 6 で照合するので、測った時刻と対象を添えて手元に残す。** 行数やファイル数は、作業ツリー・`HEAD`・リモートのどれを測ったかで違う値になる。「`SKILL.md` 268 行」とだけ書くと、後任が `git show HEAD:` で測って 266 を得たときに、どちらかが誤りに見える。実際はどちらも正しい。文書に書いて終わりにすると、後任の要約が正しいか判定できなくなる。時刻が無いと、値が食い違ったときに「後任が測り損ねた」のか「その間に変わった」のか切り分けられない。作業ツリーの変更ファイル数は数分で動く。

## Step 3: 後任のタブと pane を作る

```sh
herdr tab create \
  --workspace "<workspace_id>" \
  --label "<label>" \
  --cwd "<path>" \
  --no-focus
```

`--workspace` は self なら `$HERDR_WORKSPACE_ID`、child なら子の `workspace_id`。`--cwd` は Step 2 の `dir` と同じ。`--no-focus` は前任の視界を奪わないため (Step 6 の検証まで前任は生きている)。

label は **policy の `<session-slug>` と一致させる**。handoff ファイル名の主キーがタブ名なので、ずれると後任が自分の引き継ぎ文書を別名で保存し、次の世代が読めなくなる。世代が分かる形にする (`ABC-123-orch2` など)。

出力は JSON。`tab_id` と `pane_id` は**必ず応答から読む**。`wA:t3` のような形から自分で組み立てない:

```sh
.result.tab.tab_id        # 例 wB:t6
.result.root_pane.pane_id # 例 wB:pA
```

`tab_id` と `pane_id` は**別の階層に入っている**。`.result.pane_id` は存在しないので、平らに読もうとすると空が返る。応答から取れなかった場合は `herdr pane list` から `tab_id` で引く (`herdr tab get` は pane を返さない)。

## Step 4: 後任を起動する

```sh
herdr agent start <agent-name> \
  --kind claude \
  --pane "<pane_id>" \
  --timeout 180000 \
  -- --model 'claude-opus-5[1m]'
```

**`--model` を渡さないとモデル選択画面で止まる。** `agent start` は素の `claude` を起動するので、前任がシェルで選んだモデルは伝わらない。この段の失敗はここが一番多い。

`[1m]` は zsh の glob 文字。**シングルクォートを外さない。** 外すと展開されて消え、200K で立つ。引き継ぎ先が 200K だと、渡した直後にまた逼迫する。

`--timeout` の既定は 30000 で、上限は 300000。起動直後に読み込むものが多い後任は 30 秒に収まらないことがあるので 180000 を渡す。

agent 名は **小文字始まり・`[a-z0-9_-]` のみ・1〜32 文字**。label が `ABC-123-orch2` なら agent 名は `abc-123-orch2`。大文字を混ぜると `invalid_agent_name` で弾かれる。

### 起動に失敗したときはタブを作り直す

**一度失敗すると、agent 名が確保されたまま残り、pane も使用不能になる。** 別名で再試行しても `agent_pane_busy` で通らない。同じ pane を粘って直そうとする方が時間を食う:

```sh
herdr tab close "<tab_id>"
```

を実行して **Step 3 からやり直す**。作りかけのタブを残すと、後で一覧に読めないタブが並ぶ。

## Step 5: 起動プロンプトを投入する

### 5-1. セッション名を固定する

```sh
herdr agent prompt <agent-name> "/rename <label>"
```

本命の本文より**先に**送る。Claude Code はセッション名が未設定だと直近の作業を要約したタイトルを出し続けるので、サイドバーの表示が作業のたびに変わり、どのタブが何代目か読めなくなる。label は Step 3 と同じものを使う。

**送信が終わるのを確認してから 5-2 に進む。** `agent prompt` を連続で撃つと、1 通目が送信される前に 2 通目が入力欄へ届き、**2 つが連結したまま未送信で残る**。`agent_status` は `idle` を返し、コマンドも成功を返すので、送ったつもりのまま気づけない (`herdr agent read` で入力欄を見ると `dot-handoff-skill-2前任セッションからの引き継ぎです。` のように繋がっている)。

タイトルが変わるのを待って確認する:

```sh
for i in $(seq 1 15); do
  t=$(herdr agent get <agent-name> | jq -r '.result.agent.terminal_title_stripped')
  [ "$t" = "<label>" ] && break
  sleep 1
done
```

入力欄が汚れてしまったら、送り直す前に消す:

```sh
herdr agent send-keys <agent-name> esc
```

### 5-2. 本文を投入する

**本文はファイルに書いて `$(cat ...)` で渡す。**

```sh
herdr agent prompt <agent-name> "$(cat "$prompt_file")"
```

二重引用符に本文を直接埋めると、**バッククォートが zsh のコマンド置換として評価される**。引き継ぎ文書やその要約にはコード片・パス・コマンド例が入るので、直書きすればほぼ必ず踏む。評価された結果は静かに本文へ混ざるので、投入した側は気づけない。

本文には `--wait` を付けない。前任は Step 6 の検証まで制御を持っておく必要がある (後任の作業が終わるまで前任が固まると、検証も後始末もできない)。5-1 の完了確認とは別の話で、あちらは省くと投入そのものが壊れる。

本文に入れる 5 点:

```
1. 読む資料の順序
   - 引き継ぎ文書 (絶対パス)
   - 関連する設計文書・issue (パス / URL のみ)

2. 前任が踏んだ罠
   文書にも書いてあるが、要点をここにも再掲する。起動直後に必ず目に入る
   場所に置かないと、資料を読む前に同じことをやる

3. 役割と、触ってよい範囲
   触らないものも明示する

4. いまの状態
   Step 2 の実測値。ここは要約でよい (正は文書側)

5. 最初にやること
   「資料を読み、状態を自分で実測して要約し、そこで止まって指示を待つ」
   実測せず文書を鵜呑みにしない、と明示する
```

**勝手に進ませない。** 逼迫状態で書かれた引き継ぎは、前任の判断が既に劣化している前提で扱う。後任がそのまま走り出すと、誤りが検証されないまま増幅する。

## Step 6: 引き継げたことを検証する

**投入して終わりにしない。** ここを飛ばすと、引き継いだつもりで壊れた文書だけが残る。

```sh
herdr agent read <agent-name> --source recent-unwrapped --lines 120
```

後任の要約を、**Step 2 の実測値と項目ごとに照合する**:

| 後任の要約 | 判定 |
|---|---|
| 実測値と一致 | 合格 |
| 文書の誤りを実測で訂正してきた | 合格。**文書の方を直す** |
| 文書の数値をそのまま復唱している | **不合格**。該当項目を挙げて再実測させる |
| 資料に触れていない | **不合格**。投入が壊れている (Step 5 の `$(cat)` を確認) |

訂正が出たかどうかを合格条件にしない。文書が正しければ訂正は出ない。見るのは**後任が自分で測ったか**の 1 点。

食い違ったら、**先に時刻を確認する**。Step 2 から Step 6 までの間に前任が commit・編集をしていれば、両方の値が正しいまま食い違う。時刻で説明がつく差を「後任の誤り」として差し戻すと、後任は正しい実測を捨てて文書の古い値に合わせにくる。

不合格なら、後任を落とさず該当項目だけ指定して測り直させる。ここで妥協して先に進むと、次の世代で同じ誤りが再生産される。

## Step 7: 続きの指示を投入する

要約で止めたままにしない。後任は「止まって待て」と言われた状態なので、次を渡すまで動かない。

渡すもの:

- **次に何から始めるか** — 残作業の一覧ではなく、着手する 1 つ
- **前任が破った作法** — Step 1 の「踏んだ罠」のうち、後任が同じ状況に入るもの。実例つきで渡す。型だけ渡しても再現を防げない

投入方法は Step 5 と同じ (ファイル経由)。

## Step 8 (child モードのみ): 旧セッションを落とす

Step 6 に合格してから落とす。順序を逆にすると、検証が不合格だったときに戻る先が無くなる。

```sh
herdr tab close "<old_tab_id>"
```

worktree は**残す** (後任が同じ worktree で作業を続ける)。Linear も触らない (同じ issue が続いているので In Progress のまま)。

self モードでは自分を落とさない。Step 7 まで終えたことをユーザーに報告し、終了してよいかは本人に委ねる。

## やらないこと

- **child モードで親が引き継ぎ文書を代筆する** — 罠は子の中にしかない。外形だけ書き写した文書は、状態の要約でしかなくなる
- **後任に worktree を作らせる** — 同じ作業の続きなので、既存の worktree に入る。新しく切ると未コミットの変更が置き去りになる
- **起動失敗を `--force` や別名で押し通す** — `agent_pane_busy` は pane が壊れている合図。タブを作り直す
- **Step 6 の前に前任を落とす** — 検証に失敗したとき、状態を知っている側が居なくなる
- **`--wait` を付けて投入する** — 前任が後任の応答を待つ間、検証も後始末もできない

## 失敗時

- `agent_pane_busy` / 名前が既に使われている → 起動が一度失敗している。`herdr tab close` して Step 3 からやり直す
- 後任がモデル選択画面で止まっている → `--model` を渡し忘れているか、`[1m]` がクォート無しで glob 展開されて消えている
- `agent start` がタイムアウト → pane はできている。`herdr agent explain` で検出状態を見て、`--timeout` を伸ばすか手動起動に切り替える
- 後任が資料に触れていない → プロンプトが空か壊れている。`$(cat file)` を使ったか、ファイルが空でないかを確認する
- 投入したのに `Ctx: 0` のまま何も起きない → 入力欄に複数の投入が連結して残っている (5-1 の完了確認を飛ばした場合)。`herdr agent send-keys <name> esc` で消し、タイトル確認を挟んで送り直す。`agent prompt` は成功を返し `agent_status` も `idle` なので、送信結果からは気づけない
- `@{u}` でエラー → upstream 未設定。`origin/<default-branch>...HEAD` に替える。0 と書かない
- 子がパスを返さない (child, Step 1) → 子が `blocked` の可能性がある。`herdr agent read` で止まっている理由を見てから、文書執筆を再依頼する
